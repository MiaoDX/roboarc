## Goal

Let a user see the complete RoboArc flow early: author or select a workflow,
run it through the Runtime, observe capability progress and robot state, and
review the result in a time-aligned visualization. The first version must work
without making a browser-native 3D viewer a prerequisite.

## Recommended Shape

```text
Workbench / CLI
    -> Workflow IR + Runtime events
    -> capability adapter
    -> simulator or deterministic state source
    -> telemetry bridge
    -> Rerun log / Web viewer or standalone viewer
```

RoboArc owns the capability and telemetry contracts. The simulator owns physics
and native robot state. Rerun is the first observation backend; RViz remains a
ROS engineering/debug tool, and Gazebo is the initial ROS-native simulation
backend rather than the product UI.

## Phases

### Phase 1 - Deterministic Observable Loop

- Define a repository-local telemetry vocabulary for pose, trajectory, action
  state, progress, timestamps, and run/node/invocation identity.
- Add a deterministic simulated state source or adapter that can execute one
  narrow workflow without ROS or a heavyweight simulator.
- Emit telemetry alongside existing Runtime events without changing Workflow IR
  or core runtime state semantics.
- Log the trace to Rerun-compatible data and provide one documented viewer path.
- Prove that a run can be replayed and correlated with Workflow node events.

### Phase 2 - TIAGo ROS/Gazebo Backend

- Create a TIAGo profile with the first narrow capabilities:
  `navigation.goto_location`, `navigation.stop`, `head.look_at`, and
  `speech.say`.
- Reuse the v0.1c ROS lifecycle adapter boundary and telemetry vocabulary.
- Run the same smallest workflow against TIAGo in Gazebo/ROS 2 Jazzy.
- Capture ROS pose/TF/action feedback into the same Rerun observation path.
- Keep Gazebo GUI and RViz available for engineering diagnosis, but do not make
  either the Workbench's primary UI surface.

## UI Boundary

- The Workbench remains responsible for authoring, profile selection, run
  controls, Runtime status, progress, logs, errors, and result summaries.
- A run may expose an `Open observation` action that opens a Rerun Web Viewer
  session or a documented standalone viewer.
- Embedding Rerun inside the Workbench is explicitly optional in this plan. It
  becomes a follow-up only after the standalone observation flow proves useful.
- A browser-native 3D renderer is out of scope for v0.2a.

## Non-Goals

- Replacing Gazebo, ROS 2, RViz, or Rerun with a new rendering stack.
- General ROS topic/service support or generic telemetry ingestion.
- Full TIAGo manipulation, perception, SLAM, MoveIt, or hardware control.
- Making simulator dependencies part of core installation or always-on CI.
- Adding telemetry fields to the public Workflow IR, runtime state enum, or
  capability manifest until the observation contract is proven.
- Choosing a permanent embedded-vs-external viewer based on aesthetics alone.

## Acceptance Criteria

- A deterministic workflow produces Runtime events and time-aligned telemetry
  for at least one robot pose/trajectory and one capability progress stream.
- A human can run the documented command and inspect the resulting trace in a
  Rerun viewer without installing the core package's simulator dependencies.
- Workflow node IDs, invocation IDs, timestamps, progress, and terminal result
  remain correlated in the observation output.
- The same observation vocabulary is usable by the later TIAGo/Gazebo backend.
- No ROS imports enter `roboarc.contracts` or `roboarc.runtime`.
- Core Python/Web tests remain runnable without ROS, Gazebo, MuJoCo, or Rerun.
- TIAGo/Gazebo integration remains a separate scheduled/manual proof lane.

## Decisions And Defaults

- First observation backend: Rerun, because it supports time-series/spatial
  traces and can be consumed through a Web Viewer or standalone viewer.
- First ROS simulation backend: Gazebo, because TIAGo's ROS-native stack aligns
  with Nav2, controller, sensor, and Action validation.
- RViz: supported as an external developer tool, not a Workbench dependency.
- MuJoCo: deferred to the v0.3 portability/SDK path unless a concrete Phase 1
  experiment shows a better fit for the first deterministic loop.
- Viewer placement: external/opened-from-Workbench by default; embedding is a
  reversible follow-up decision.

## Risks And Stop Gates

- Stop before adding public telemetry contracts if correlation cannot be
  expressed without changing existing Runtime/IR semantics.
- Stop before installing a full simulator if a deterministic state source can
  satisfy the Phase 1 acceptance criteria.
- Re-approve scope before adding embedded viewer infrastructure, multiple
  containers, hardware, paid services, or cross-host DDS/networking.
