# v0.3 Portability Proof

## Plan Ledger

- Status: IMPLEMENTED - Reachy 2 SDK/MuJoCo portability proof completed
- Roadmap owner: `docs/development-plan.md` v0.3
- Scope source: v0.2 TIAGo evidence, capability model, and planning-loop review
- Goal: prove that profile-appropriate Workflow IR documents can be selected,
  preflighted, and executed against TIAGo/ROS and Reachy 2's SDK-facing
  interface through the same core contracts, with correlated visual evidence,
  without moving ROS/vendor dependencies into the core runtime.

## Decisions

- Profile selection is process/startup scoped: one active profile owns one
  runtime. The operator chooses the target robot before starting the service;
  per-run adapter switching and live robot switching are out of scope.
- Each robot adapter registers its own exact-version capability set. The
  Workbench shows only capabilities exposed by the active profile and does not
  display unavailable TIAGo or Reachy 2 capabilities.
- Portability means that different robot-specific workflows use the same typed
  Workflow IR, Runtime lifecycle, validation, event, telemetry, and review
  contracts. It does not require TIAGo and Reachy 2 to expose identical
  capabilities, execute the same workflow, or produce the same demonstration.
- Reachy 2 is the only second robot in v0.3. The product proof uses Pollen
  Robotics' official Docker image, MuJoCo simulator, and SDK/gRPC interface.
  Gazebo/RViz remain optional engineering diagnostics, not a second product
  proof.
- A deterministic in-process Reachy-SDK-shaped fake provides always-on tests,
  but it cannot satisfy the v0.3 product acceptance gate by itself.
- When the official Docker image is unavailable to the execution environment,
  the supported development fallback is the repository's minimal self-built
  MuJoCo lane. It pins the open-source `reachy2_mujoco` and
  `reachy2_symbolic_ik` commits, MuJoCo version, base image digest, and the
  bounded source patch required to start the upstream scene.
- Compatibility is conservative and deterministic: `compatible`, `missing`,
  `incompatible`, or `unknown`, with machine-readable reasons. v0.3 does not infer
  semantic equivalence from IDs and versions alone, and does not claim support
  for dimensions absent from the manifest contract.
- Existing Workflow IR and manifest schema version 1 remain backward
  compatible. Any added compatibility metadata must be minimal, optional, and
  schema-tested.

## Scope

### Phase 1 - Profile and Compatibility Contract

- Define a stable startup configuration such as `roboarc serve --profile
<profile-id>` while retaining one active adapter per process. Keep the Runtime
  API singular: it reports the active profile and does not switch adapters.
- Define a node-keyed compatibility report with status, capability reference,
  and reason codes for workflows loaded from another profile; missing,
  unknown, or incompatible nodes fail preflight before run.
- Pin the selected profile ID into run metadata and preserve exact
  `{id, version}` references.
- Add contract/schema tests for profile discovery, selection, report output,
  and backwards compatibility with current manifests.

### Phase 2 - Second Native Interface Proof

- Prefer the official `docker.io/pollenrobotics/reachy2` image pinned by
  immutable digest when access is available. Otherwise build
  `docker/reachy2-minimal` from fixed upstream commits; record its base image
  digest, architecture, startup arguments, and the intentionally smaller
  surface (MuJoCo fake SDK server plus virtual display, without ROS/RViz/VNC).
- Implement the Reachy 2 SDK adapter outside `roboarc.contracts` and
  `roboarc.runtime`, using the existing `CapabilityAdapter` lifecycle; provide
  an in-process SDK-shaped fake for always-on tests.
- Probe the official SDK/MuJoCo interface and record the Reachy 2 capability
  matrix covering IDs, inputs/outputs, frames/units, progress, cancellation,
  visual observability, and semantic assumptions. Register only capabilities
  the adapter actually implements.
- Implement a narrow, visually meaningful Reachy 2 workflow with deterministic
  behavior and the same observable Runtime event/result contract. Do not copy
  the TIAGo workflow merely to create superficial capability overlap.
- Add adapter conformance tests covering validation, terminal results, progress,
  timestamps, cancellation traits, and error propagation where supported.
- Run the selected workflow against the official Reachy 2 MuJoCo simulator and
  SDK interface as a manual/scheduled product gate; it must not become a core
  installation or always-on CI requirement.
- Capture a fixed, reviewable simulator recording plus same-run Workflow IR,
  result, JSONL, native Rerun, and UTC media-origin metadata.

### Phase 3 - Workbench and Proof Integration

- Fetch and display the process-selected active profile before a run; the
  Workbench does not switch adapters.
- Build the Blockly toolbox from only the active profile's registered
  capability manifests.
- Show per-node compatibility status and machine-readable reasons before Run.
- Ensure validation and execution use the selected active profile consistently.
- Add API, Web unit, and Chromium coverage for profile selection, blocked
  incompatible workflows, and successful cross-adapter execution.
- Reuse the manifest-backed review route and Execution Timeline so Reachy 2
  video playback and seeking highlight the active Blockly node.
- Document reproducible commands and the boundary between always-on fake tests
  and the required manual/scheduled official MuJoCo product proof.

## Non-Goals

- Per-run profile switching, multi-robot orchestration, or live adapter reload.
- Full semantic portability for frames, maps, workspace limits, payloads,
  preconditions, or robot-specific safety behavior not represented in v0.3
  metadata.
- A universal capability catalog or forced TIAGo/Reachy capability parity.
- Manipulation, perception, SLAM, MoveIt, and hardware control in the initial
  Reachy visual proof.
- New Workflow IR control-flow nodes, expressions, variables, loops, retries,
  fallbacks, parallelism, subflows, persistence, auth, or scheduling.
- Embedding noVNC, Gazebo, MuJoCo, or another live 3D stream in the Workbench.
- A second Reachy Gazebo product lane; Gazebo/RViz may be used only for
  engineering diagnosis.
- Loading arbitrary adapters or code supplied by a remote client.

## Acceptance Criteria

- A documented profile selection/configuration returns a stable active profile;
  the selected profile is visible in the Workbench and pinned in run metadata.
- Compatibility is deterministic, node-keyed, machine-readable, and blocks
  runs with missing or incompatible capability references before execution.
- The TIAGo and Reachy workflows may use different registered capabilities, but
  both validate and succeed through the same Workflow IR and Runtime contracts,
  with matching lifecycle/event invariants and preserved node/invocation
  identity.
- The Workbench toolbox contains exactly the active profile's capability set;
  loading a workflow with unavailable capabilities reports incompatibility and
  cannot start an invocation.
- The core package remains ROS/vendor-free; the second adapter is isolated from
  `roboarc.contracts` and `roboarc.runtime` according to the existing boundary.
- Python, schema, API, Web unit, and Chromium checks pass without simulator or
  hardware dependencies.
- The official Reachy 2 MuJoCo lane, or the documented fixed-commit self-build
  fallback when official image access is unavailable, runs through the SDK-facing adapter and
  produces a successful same-run manifest, JSONL, Rerun recording, and playable
  simulator video with visible robot behavior.
- The Reachy review page keeps the larger simulator recording beside the
  smaller synchronized Blockly panel, matching the reusable TIAGo review
  contract rather than adding a robot-specific UI.
- The Reachy image digest (official, or self-build base), scene, platform, launch arguments, dependency
  versions, capture dimensions/codec/duration, and GPU/software-rendering mode
  are recorded so another supported host can reproduce the proof.

Additional v0.3 gates:

- CLI/config and API contract tests cover startup profile selection, active
  profile reporting, and compatibility reasons.
- Cross-adapter conformance tests execute profile-appropriate Workflow IR
  documents and compare required Runtime lifecycle/event/result invariants,
  without requiring identical capability references.
- Import-boundary tests prove no ROS/vendor imports enter core contracts or
  runtime modules.
- A negative fixture proves an incompatible capability is rejected before any
  invocation starts.
- The required Reachy SDK/MuJoCo product check is explicitly manual or scheduled
  and records dependency/runtime versions; it remains outside core CI. The
  self-build fallback must record source commits and its own image digest.
- Media validation proves readable frames, expected codec/resolution/duration,
  and non-static robot behavior during active workflow nodes.
- Browser verification proves same-run artifact loading and video-to-Blockly
  highlighting on playback and seek.

## Risks And Stop Gates

- Stop for user review if profile selection must become per-run; that requires a
  different runtime and adapter lifecycle.
- Stop before expanding manifest semantics if compatibility requires frames,
  maps, limits, or preconditions that cannot be represented minimally and
  backwards-compatibly.
- Stop if neither the official Reachy image nor the fixed-commit self-build can
  be reproduced, the MuJoCo/SDK path cannot produce visible correlated behavior,
  or the proof requires physical hardware, credentials, or an unpinned dependency.

## Parked Follow-Up

After v0.3 evidence, reassess cross-profile capability standardization, richer
semantic metadata, per-run profile orchestration, production Reachy hardware
support, and v0.4 programming-model features as separate proposals.
