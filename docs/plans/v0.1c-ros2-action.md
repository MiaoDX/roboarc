## Goal

Prove that RoboArc's existing `CapabilityAdapter` and `CapabilityInvocation`
lifecycle can drive one genuine ROS 2 Action end to end without changing
Workflow IR or coupling the runtime core to ROS.

The proof must observe goal dispatch, native feedback, terminal results,
cancellation request disposition, terminal cancellation acknowledgement,
server unavailability, and bounded timeout cleanup through the same runtime
and event contracts already exercised by MockAdapter.

## Why This Milestone Exists

MockAdapter proves internal semantics but cannot prove that the abstraction
matches a real asynchronous robot transport. v0.1c is deliberately smaller
than TIAGo: it isolates the lifecycle mismatch risk before simulator setup,
robot-specific capability contracts, and navigation semantics are introduced.

## Scope

- A test-only, repository-local ROS integration harness outside
  `src/roboarc/contracts` and `src/roboarc/runtime`; it is not a distributable
  ROS package and does not add `rclpy` to core package metadata.
- One narrow ROS 2 Action-backed capability and robot profile used only for
  lifecycle proof, not presented as a shared robot capability standard.
- A deterministic ROS 2 Action test server capable of success, abort/failure,
  feedback, cancel acceptance/completion, non-cooperation, delayed completion,
  and unavailable-server scenarios.
- Translation from ROS goal/result/feedback/status into current RoboArc
  invocation, progress, result, error, timeout, and cancellation contracts.
- Adapter-focused tests plus one end-to-end Workflow IR -> Runtime -> ROS 2
  Action -> terminal result proof.
- Setup and test documentation that keeps ROS tooling optional for core users.

## Non-Goals

- TIAGo, Nav2, MoveIt, Gazebo, hardware, or a production robot adapter.
- New Workflow IR nodes, runtime states, event types, or capability manifest fields.
- Declaring `navigation.*`, `head.*`, or `speech.*` semantics stable.
- General ROS topic/service support, adapter plugin discovery, or multi-profile UI.
- Making ROS a dependency of the base `roboarc` package or always-on core CI.
- Retry, pause/resume, durable restart, parallelism, or resource scheduling.

## Invariants To Protect

1. `roboarc.contracts` and `roboarc.runtime` import no ROS modules.
2. The existing Workflow IR and exact `{id, version}` reference execute unchanged.
3. Cancel acceptance is reported separately from confirmed terminal cancellation.
4. Timeout never claims the native goal stopped unless ROS reports a terminal state.
5. The adapter validates and normalizes successful output through the current manifest.
6. Core Python/Web tests remain runnable without ROS installed.

## Proposed Architecture

```text
Workflow IR
    -> RoboArc Runtime (ROS-free)
    -> CapabilityAdapter protocol
    -> repository-local ROS 2 test harness
    -> rclpy ActionClient
    -> deterministic ROS 2 Action test server
```

The test harness owns ROS node/executor lifecycle, ActionClient goal
handles, feedback callbacks, status mapping, and cleanup. The core runtime owns
validation, deadline policy, event ordering, and final execution state exactly
as it does for MockAdapter.

## Planning-Loop Decisions

The planning loop and user review resolved these implementation boundaries:

1. **Environment lane:** ROS 2 Jazzy on Ubuntu 24.04 with Python 3.12 is the
   sole proof lane. This avoids the Python 3.10 mismatch of Humble while
   matching one supported RoboArc interpreter.
2. **Package boundary:** repository-local, test-only harness; core installation
   remains ROS-free.
3. **Action contract:** use `example_interfaces/action/Fibonacci`; do not add a
   custom interface package for this spike.
4. **Executor ownership:** the harness owns a dedicated single-threaded
   executor, node, and spin lifecycle with deterministic shutdown.
5. **Outcome mapping:** use existing `ResultStatus.FAILURE` and
   `ErrorCode.CAPABILITY_FAILED` with stable JSON details for goal rejection,
   unavailable server, abort, and transport exceptions; add no public error
   codes or states. A per-request ROS cancel rejection cannot be represented by
   the current `CancellationDisposition` and is outside this proof.
6. **Cancellation:** accepted cancel is non-terminal; terminal canceled is
   reported only after the native goal reaches that state. Accepted-but-never-
   terminal goals use existing grace expiry, `detach()`, and
   `cancellation_incomplete` behavior.
7. **CI tier:** add a separate Jazzy workflow using the same container command
   as local development. It must not join the always-on core Python matrix.

## Container And CI Contract

- Build one repository-owned image from an Ubuntu 24.04 / ROS 2 Jazzy base;
  Python 3.12, RoboArc, ROS test dependencies, and pytest run inside it.
- Run the ActionClient adapter and deterministic Action test server in the same
  container with separate ROS nodes/executors. v0.1c needs neither Compose nor
  host networking because it does not test cross-host DDS discovery.
- Use one documented container command as the acceptance gate locally and in
  CI. Local development may mount the checkout for iteration; CI tests the
  checked-out commit in a clean image.
- Keep the host Ubuntu 22.04 / ROS 2 Humble installation outside acceptance.
  It may be used for non-blocking experiments but must not change supported
  RoboArc Python versions or the canonical proof result.
- Put the container check in a dedicated ROS workflow, separate from
  `core-ci`. Multi-container orchestration remains deferred to v0.2 simulator
  work.

## Acceptance Criteria

- The same current Workflow IR/runtime code used for MockAdapter invokes one
  real ROS 2 Action capability without core conditionals for ROS.
- Native feedback appears as RoboArc progress with correct provenance.
- Succeeded, aborted/failed, rejected/unavailable, canceled, timed out, and
  cleanup-incomplete scenarios are distinguishable at the RoboArc boundary.
- A cancellation request is never treated as terminal cancellation before the
  native goal reaches a terminal canceled state.
- All locally owned ROS nodes, executors, threads, observers, and futures
  terminate. An unconfirmed remote/native goal may continue after `detach()`
  and must be reported as `cancellation_incomplete`.
- A no-ROS environment can install the core package and run its existing tests.
- Focused ROS integration commands are deterministic and documented.

## Outcome Mapping

The adapter must preserve this table without changing public contracts:

| ROS condition | RoboArc result | Error details | Terminal? |
|---|---|---|---|
| Goal accepted, ROS result succeeded | `success` | validated output | yes |
| Goal accepted, ROS result aborted | `failure` | `ros_status: aborted` | yes |
| Goal rejected or server unavailable | `failure` | `ros_status: rejected` or `server_unavailable` | yes |
| Cancel accepted, goal reaches canceled | `canceled` | `ros_status: canceled` | yes |
| Timeout, native terminal observed during grace | `timeout` | `capability_timeout`, terminal status | yes |
| Timeout/grace expiry without native terminal state | `failure` | `cancellation_incomplete`, native status | yes at RoboArc boundary |
| ROS transport/client exception | `failure` | `ros_status: transport_error`, stable message | yes |

## Risks And Stop Gates

- Stop if the current adapter protocol cannot truthfully represent a native ROS
  lifecycle without a public contract change; return with evidence before editing core.
- Record a ROS per-request cancel rejection as evidence for that stop gate; do
  not map it to `UNSUPPORTED`, add a new disposition, or claim support in v0.1c.
- Stop before adding a production capability ID or TIAGo-specific dependency.
- Stop if ROS distribution/Python compatibility would force a supported-core
  Python downgrade or global dependency change; keep the integration isolated.
- Stop before making a slow container or ROS installation mandatory in always-on core CI.
- Park ergonomics, generalized ROS transports, plugin loading, and simulator work.
